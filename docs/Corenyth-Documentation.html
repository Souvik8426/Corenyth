Updated Oct 30, 2026 from branch beta_version (base commit e64cad7, plus uncommitted mood-model retrain and native speed-up; see section 18).

Diagrams need internet to load Mermaid.js; the diagram source text is shown instead.

1. What Corenyth is

  • Personal assistant that runs fully on an Android phone (Android 7.0+, API 24+).
  • No account, no cloud, no INTERNET permission.
  • Keeps tasks, exact reminders, personal facts; proactive follow-through check-ins.
  • Fine-tuned Qwen3 0.6B (Q4_0 GGUF, 381 MB) runs on phone CPU via llama.cpp (libllama_jni.so + runtime-selected libggml-cpu-*.so variants, b11541). It emits a mascot mood envelope first in every reply. Gemma 4 E2B is kept as an experimental, slower option.
  • Design rule: the model interprets, code acts.
  • Package com.corenyth.assistant, v0.2.0+2, branch beta_version, Apache-2.0.

3. Request pipeline (one message)

flowchart TD
 U[User types message] --> SC{Scope check core_policy}
 SC -->|clearly outside, 1st time| RF[One-line refusal, AI does not run]
 SC -->|outside, user persists| RO[Model answers read-only, no data changes]
 SC -->|core or unsure| R{Simple case?}
 R -->|yes| RE[Rule engine instant]
 R -->|no| M[Qwen3 0.6B: GBNF JSON plan]
 M --> V{Code validates plan vs text + DB}
 V -->|valid| X[Execute tools]
 V -->|unsafe / invalid| RE
 RE --> X
 X --> DB[(Local SQLite)]
 X --> AL[Schedule Android exact alarm]
 X --> C[Honest confirmation]
 C -.background.-> MO[Mascot mood update]
  • 1 Scope check: core / clearly outside / unsure.
  • 2 Outside first time: one line refusal, model skipped.
  • 3 Core: rules handle simple cases, else model plans, code validates, rules take over on bad plans.
  • 4 Code writes DB + schedules alarm; honest reply e.g. "Saved, but notifications are blocked".
  • 5 Mood updates in background so replies stay fast.
  • 6 When due, Android fires it even if the app is closed.

6. Core rules and core policy

stateDiagram-v2
 [*] --> InScope: reminders/alarms/tasks/notes/schedule/facts
 InScope --> [*]: normal concise reply
 [*] --> Refused: out of scope, first ask
 Refused --> Answered: repeats similar ask or says answer anyway
 Answered --> [*]: model answers read-only
 Refused --> [*]: user moves on
 note right of Refused: refusal remembered per chat (resets on app restart)
  • Scope: reminders, alarms, tasks, notes, schedule, saved facts.
  • Exact line: "That's not in my core functionality. I can help with: reminders, alarms, tasks, notes, your schedule, and facts you've saved."
  • Persisted answers can be fuller, never change data.
  • Replies short; length cap lifted when user asks for detail (grapheme-aware budget).
  • Always on, no toggle. Source: CORE_RULES.md, lib/assistant/core_policy.dart.
  • Limits: refusal memory resets on restart; word rules can't classify every sentence.

13. Privacy and permissions

  • Permissions: POST_NOTIFICATIONS, SCHEDULE_EXACT_ALARM, RECEIVE_BOOT_COMPLETED, BIND_REMOTEVIEWS (widget).
  • No INTERNET, mic, camera, contacts, location, analytics or crash reporting.
  • Feedback opens your own mail app draft.

18. Report: mood model and speed-up (Oct 30)

Goal

  • The on-device model emits a mascot-readable envelope {"emotion":{"mood","intensity","confidence"},...} first in every reply, in the user's chosen personality (loving / professional / caring / friendly), for both prompt contracts (plan and reply).

What was done

  • Dataset: 4000-row personality set + mood rows (GoEmotions-derived) + reply rows, built by build_dataset.py, build_chat_rows.py, make_bundle.py; prompts are byte-identical to the Dart renderers (app_prompts.py, export_prompts_test.dart).
  • Gemma 4 E2B: LoRA merged on Mac (merge_lora.py), quantized to Q4_0 (3.36 GB) and run on the POCO F5. Works but too slow, so kept as an experimental catalog entry (no download URL).
  • Qwen3-0.6B retrain (default): LoRA r=32, alpha 32, all projections, lr 2e-4 cosine, 2 epochs, loss on completion only, Colab T4 via Unsloth (colab_cells.py). Exported Q4_0, 381,566,592 bytes, allowlisted in model_status.dart; tests updated.
  • Mac training: train_mac.py (MPS) works but is about 52 s/step (about 13 h/epoch), so Colab is used for training; Mac is used for merge/convert/quantize.
  • Phone check: mood and mascot reactions correct on three prompts ("got the job", "dog is sick", "remind me to call mom"). The job reply wording ("relief/lucky") is off, so quality needs a wider check.

Speed work (POCO F5, Snapdragon 7+ Gen 2, 4 threads, about 1.15k-token prompt)

  • Change: llama/ggml are now shared libs with GGML_BACKEND_DL + GGML_CPU_ALL_VARIANTS (baseline, dotprod, i8mm, SVE variants). llama_jni.cpp loads the variants from its own folder (dladdr + ggml_backend_load_all_from_path); build.gradle.kts sets useLegacyPackaging = true so the libs are extracted. Phones without dotprod fall back to baseline instead of crashing.
  • Result: prompt processing about 2x faster. Decode did not improve (about 4 tok/s in every build; the earlier 6-7 tok/s was probably a cooler phone, unconfirmed).
  • Turn time now: cold about 24 s, warm about 14 s. Reply generation (about 44 tokens, about 10-11 s) is the main cost; the 4 s target needs shorter replies and a shorter envelope in the training data, then a retrain. Lowering maxTokens alone does nothing since typical replies are far below the cap.

Verification

  • flutter test: 538 pass, 3 skipped. flutter analyze: 0 errors, 0 warnings (111 existing infos, identical before the changes).
  • On phone: model loads and answers with the new native libs; two prompts timed. Not tested: a phone without dotprod/i8mm (fallback path), which variant was picked on the POCO F5 (timings look like dotprod, not i8mm), Windows/macOS.
